API and tokens

Connect Youm to your tools with a personal token, and receive a project’s changes by webhook.

The Youm API lets a script or a tool read projects and stories, and send the same commands as the application: propose a story, create a task, move it forward. It is off by default, and appears nowhere until an administrator turns it on.

Turn on API access

The owner and administrators turn access on from the Members page: Organization settings, API access section, by ticking Allow API access. The same section lists the organisation’s tokens, with their holder, their scope and when they were last used. An administrator can revoke any of them.

Unticking the box turns access off: every token of the organisation stops working at once. Ticking it again restores them, except those that expired or were revoked in the meantime.

Create a token

Once access is on, every member finds the API tokens section in My account. A guest, from outside the organisation, does not have it. New token opens a window:

  1. Give the token a name that says where it is used.
  2. Choose its Scope: Read, or Read and write.
  3. Choose its Duration: 30, 90 or 365 days. A token always expires.
  4. Choose Create the token, then copy it before closing the window.

The token is shown only once. Youm keeps only a fingerprint of it, and the list shows only its last four characters. If it is lost, revoke it and create another one. Each person can have ten active tokens per organisation.

What a token can do

A token acts with the rights of the person who created it, in their organisation only. It sees only what they see, and every command goes through the same rules as in the application. What it creates is signed with that person’s name.

Some actions remain a human gesture, and a token is refused for:

  • submitting a story for validation, validating it, requesting a correction, waiving a test or cancelling a validation;
  • inviting, removing a person, transferring or deleting the organisation, and turning API access off.

If the person leaves the organisation, their tokens stop working.

Call the API

Every request carries the token in the Authorization header. Paths start with /v1. For example, to list the organisation’s projects:

curl -H "Authorization: Bearer youm_…" https://api-youm.mowoapp.com/v1/organizations/atelier-demo/projects

All writes go through POST /v1/commands, which receives a command in JSON:

curl -X POST https://api-youm.mowoapp.com/v1/commands \
  -H "Authorization: Bearer youm_…" -H "Content-Type: application/json" \
  -d '{"type":"proposeStory","projectId":"…","title":"Pay an invoice online","why":"","kind":"userStory"}'

A refusal returns a stable coded reason and a message in French. The full API description, in OpenAPI format, is at /v1/openapi.json, without a token. The API description link, in My account, leads to it.

A token is allowed 300 requests per minute. The RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset headers say where it stands. Beyond that, the 429 response gives in Retry-After how many seconds to wait.

Declare an agent

An agent is a non-human member of the organisation: an artificial intelligence tool or a maintenance bot, for example. It works through a service token, joins a team and can be responsible for tasks. It has the rights of a member, but it validates nothing, does not submit a story for validation, and becomes neither Product Owner, nor Scrum Master, nor owner.

The owner and the administrators declare an agent in the API access section of the Organization settings, under Agents: a name, a duration, then Declare the agent. The service token is then shown only once. New token creates another one when the first has expired.

Then add the agent to a team, like a member. It appears everywhere under its name, marked Agent in the list of members, and receives no email. It does not count in the billed seats. Removing it from the organisation, like a member, stops all its tokens.

Open a project to agents

An agent only works in a project that has turned on the Agent development option. It is off by default, and while it is off nothing changes in the project: the agent reads nothing there, writes nothing there and is not offered as the owner of a task.

The team’s Scrum Master turns it on from the project page, once the organisation has declared an agent: tick The organisation’s agents work in this project. Business screens stay the same. Turning the option off leaves the work already done in place; the agent no longer acts in the project. Each change goes into the audit log.

Whatever an agent writes carries the mention Written by AI next to its name: a story it created, a comment, a task, a history line. In lists and on the Task Board, the mention shrinks to AI. It is always there and has no setting; as long as no agent writes, it appears nowhere.

When an agent has finished an In progress story, it marks it Ready for review. This is not a state: the story stays In progress, and only a human moves it forward. A team member reviews the work, then moves the story to Awaiting validation; it then shows Reviewed by with their name, in its details and its history. A team member can also remove the mark, and it disappears on its own if the story leaves In progress. Business users see none of this.

In a project open to agent development, a story’s details, technical view, include a collapsed Technical details section. The team and the Product Owner use it to spell out what the story must do for whoever builds it: desired behaviour, key interfaces, testable criteria and out of scope, in Markdown, plus three choices: implementation by an agent or by a human, size for an agent (fits in one session or to be split) and review effort. When collapsed, the section summarises the choices made. An agent can prefill it with its token, from the request’s description; what it writes is marked Written by AI in the history. Business users and stakeholders see neither the section nor its changes, and points remain the only estimate shown elsewhere.

An agent also records each work session on the story: its duration and, if it knows them, its cost, its number of iterations, the model used and a link to its trace. A team member can record one the same way, through the API. Sessions appear in the technical details, with their total next to the story’s points: the team compares what the story cost with what it had estimated. A session cannot be edited; its author or the Scrum Master removes a session entered by mistake, and the history keeps it. Business users and stakeholders do not see them.

Connect an agent through MCP

Youm serves an MCP (Model Context Protocol) server at the API’s /v1/mcp address, for example https://api-youm.mowoapp.com/v1/mcp. An agent connects with its service token, in the Authorization: Bearer youm_… header; there is nothing to install. The checks are the API’s: the token’s organization, its scope, its rate limit, and the project’s Agent development option.

The server offers nine tools. The first six follow a story’s path:

  1. list_ready_stories lists the stories ready to start: In progress in the active sprint, with no task started or taken by someone else. Each comes with its need, its acceptance tests and its technical details.
  2. get_story reads a story, with its tasks and the evidence already attached.
  3. take_story takes a story: the agent becomes owner of its free tasks, which move to In progress. A story without a task gets one, named after it.
  4. add_evidence attaches evidence of the work done: what it shows in a sentence or two, and a link to a pull request, a test result or a log. The team finds it in the technical details, marked Written by AI; business users do not see it.
  5. record_session records a finished work session: its duration in minutes (or its start and end) and, if the agent knows them, its cost and currency, its iterations, the model and a link to the trace.
  6. mark_ready_for_review marks the story Ready for review. A team member reviews it and moves it to Awaiting validation.

The other three prepare the work:

  1. list_projects lists the projects open to agent development where the agent works, with their product goal and open themes.
  2. propose_story proposes a story in one of these projects: a title, the why, the kind and, if the agent knows them, acceptance tests and a theme. The story arrives in the Suggested state, marked Written by AI; the Product Owner accepts or declines it, like any proposal, and can change its theme.
  3. comment_story adds a comment to a story of the team: a question, a decision, a blocker. It is marked Written by AI.

A read token uses only the tools that read: list_ready_stories, get_story and list_projects. Each tool has its route in the API: GET /v1/organizations/{slug}/ready-stories, GET /v1/organizations/{slug}/agent-projects, GET /v1/stories/{id}, and the takeStory, addEvidence, recordSession, setStoryReadyForReview, proposeStory and addComment commands of POST /v1/commands. An agent only proposes and comments in its team’s projects open to agents.

Agent flow

The agent flow describes what an agent does in Youm, whatever the team’s way of working. The MCP server sends it to the agent as soon as it connects, in its instructions.

StepToolWhat happens
Listlist_ready_storiesThe ready stories, by rank: the first one has the highest priority.
Taketake_storyThe agent becomes owner of the story; other agents no longer see it.
Readget_storyThe acceptance tests say when it is done, the technical details where and how to work.
Deliveradd_evidence, record_sessionThe evidence of the work and the duration of the session.
Hand backmark_ready_for_reviewA human team member reviews it and moves the story to Awaiting validation.
Proposelist_projects, propose_storyA need split into stories, which wait for the Product Owner’s decision.
Askcomment_storyA question or a decision, in the story’s discussion.

Humans keep the decisions: the Product Owner accepts proposals and orders the backlog, the team plans the sprint and moves stories to In progress, a team member validates. The agent never moves a story forward on its own.

To reserve a story for a given agent, assign one of its tasks to that agent in the Task Board: the story disappears from the other agents’ list.

Flow sheet

Copy the sheet below into the instructions file the team’s agent reads: the repository’s instructions file, the editor’s rules, the ticket tracking description. It fits any way of working once its steps are renamed with that method’s words, for example “ticket” for story or “close” for hand back.

# Work tracking: Youm

Tickets are Youm stories, read and written through the “youm” MCP server.

- Next ticket: list_ready_stories; take the first one in the list.
- Take: take_story, before any other write.
- Read: get_story. Acceptance tests are the definition of done;
  technical details give the repository, the branch and the constraints.
- Deliver: add_evidence with the pull request link, then record_session.
- Hand back: mark_ready_for_review. Never validate: a human does.
- Split a need: list_projects, then propose_story for each story.
- Ask a question or record a decision: comment_story.

Receive changes by webhook

A webhook sends the changes of a project to an HTTPS address, as they happen: a story created or changed, a task, a comment, a sprint that starts or closes. The owner, the administrators, the Product Owner and the Scrum Master of the project set them from the project page, Webhooks tab. It appears only when API access is on. Add a webhook opens a window:

  1. Enter the Address that will receive the deliveries.
  2. Tick the Events to receive.
  3. Choose Add the webhook, then copy the signing secret.

Each delivery contains the complete object, in the API format. It carries the Youm-Event header, which names the event, and Youm-Delivery, an identifier that stays the same from one attempt to the next. The Youm-Signature header lets you check that it does come from Youm: it is an HMAC SHA-256 of the body, computed with the secret. The secret is shown only once.

Only a 2xx response counts as received. Otherwise, Youm tries again after one minute, five minutes, thirty minutes and two hours. After ten failures in a row, the webhook turns off and the person who created it receives an email. Choosing a webhook in the list opens its panel: its events, its Latest deliveries (the last ten deliveries and their result), Delete, after confirmation, and Turn back on once the address can be reached again, which resumes the pending deliveries.

Turning API access off suspends all the organisation’s webhooks. If the person who created a webhook leaves the organisation, it turns off: another person in charge of the project can turn it back on, and is then answerable for it.

Revoke a token

In My account, or in the organization settings for an administrator, Revoke, then Revoke in the confirmation window. The token stops working at once. Creating and revoking a token, like turning access on, are recorded in the organisation’s audit log. Actions taken with a token appear there under its holder’s name, with the token’s name.
